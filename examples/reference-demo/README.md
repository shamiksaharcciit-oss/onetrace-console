# A reference demo: one agent, two days, one different answer

A small coding agent, recorded with [onetrace](https://pypi.org/project/onetrace/), fixes a
failing auth configuration. It is recorded as a graph:

```
           +--> context --+
request ---+--> tests ×2 -+--> model --> proposal --> config applied
           +--------------+
```

The request feeds the document search, the test run and the model; the model reads all three;
its proposal is applied. The run declares that graph as its approved plan (`declared_edges`),
and the recorder refuses, at emission, any link outside it. Each link in the record is
observed, not declared: a stage that reads another stage's receipt records that link.

The tests stage runs twice. **Its first attempt fails on purpose**: the demo raises a timeout
instead of running it, so that the record shows a retry, and the error it records says so
("set by the demo to show a retry ... nothing timed out"). The failed attempt is kept in the
record; the model reads the second attempt's results.

It runs twice, a day apart. Both times the model stage reads exactly the same data: the same
task, the same three documents and the same four failing tests. (It also reads the receipts of
the stages before it, which record their own times, so those differ by a day.) On the first
day it writes `"production"`; on the second, `"staging"`. Every stage after it changes too: a
different proposal, and a different configuration applied.

That is the case a stage-level record is for. Both runs check out on their own. Compared, they
first differ at the model stage, where the only recorded setting that differs is the model's
`seed`. What the record does not establish is *why* the model wrote what it wrote.

## What is in here

- `demo.py`: the pipeline. The model is a stand-in with no network call: it samples one of
  the values its instructions allow, with the seed its settings record. The model stage is
  declared not re-runnable, as a real sampled model call would be.
- `runs/day-1`, `runs/day-2`: the two runs, exactly as `demo.py` writes them.

## The clock

By default every time in a record is read from the clock. To produce two runs a day apart
without waiting a day, `--at` sets the clock the recorder reads to a chosen start, then one
second per reading. When it does, the first stage records the constant `clock`:

> set by the demo; the times in this record were not read from a clock

It is the same in both runs, so it is not a difference between them. The committed runs were
made with `--at`, so they can be regenerated byte for byte:

```
python demo.py runs/day-1 demo-run-1 1 --at 2026-09-28T10:00:00Z
python demo.py runs/day-2 demo-run-2 2 --at 2026-09-29T10:00:00Z
```

## Signed with a demo key (`trust.json`)

Both runs are signed: each holds
`signatures/1.json` beside its chain, an Ed25519 signature over the run's chain head. Adding it
changed no byte of the chain: the chain heads are the ones the runs had before.

**The key is a test key made for this demo, and it no longer exists.** It was generated with
onetrace's own `onetrace.signing.keygen(..., test_only=True)` in a folder outside this repository, used to sign these two runs,
and deleted. It is never reused, so the signatures cannot be made again byte for byte -- unlike the
runs themselves, which `--at` regenerates. Its public key's id is
`sha256:311dc2859bb2dfcfa2c94184b682fff3f535ec4c8867c1437a29123b4c626777`.

`trust.json` is the demo's own trust file, shipped here and nowhere else. It names that key with
the label **"test key (demo)"**, so a console or a reader given it shows the runs as "Yes · test
key (demo) · {key id}": the label says it is a demo key. Without it, the same valid signatures read
"Signed, key not trusted": the verifier knows keys, not people, and your trust file is what ties a
key to a name.

```
cd runs/day-1 && onetrace-verify --trust ../../trust.json .     # signed by test key (demo)
cd runs/day-1 && onetrace-verify .                              # signed by an untrusted key
```

Checking a signature needs the verifier's `[crypto]` extra: `pip install "onetrace-verify[crypto]"`.

## Checking and comparing them yourself

```
cd runs/day-1 && onetrace-verify .        # and the same in runs/day-2
python -m onetrace diff runs/day-1 runs/day-2 --out diff-out
```

Both runs verify. The diff compares them as graphs, node by node, and names `model` as the
first difference: every node before it is the same, and the seed is the only recorded setting
of it that differs.

The console checks each run with the pinned `onetrace-verify`, which holds. It also notes that
the reference topology check is not shipped with the pinned verifier, so the graph's links were
not checked by it; it says so as a "could not check" incident on each run, rather than passing
over it.

There are no authorization records in this demo: no policy engine is part of it.
