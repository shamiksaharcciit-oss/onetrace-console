# Changelog

## [Unreleased]

## [0.9.0] - 2026-11-18

### Added

- **Trace forwarding, set up from the Settings gear.** An admin adds OTLP endpoints at `/forwarding/setup` (LangSmith, Langfuse, a Collector and the like), and each new run is sent once to each destination that is on and takes it (every run, or only runs whose records agree), as one trace: onetrace's own export of the run with one attribute, `onetrace.console.check`, the console's result for it. OTLP over HTTP, JSON with the standard library or protobuf with the new `[otlp]` extra; https, or http only on this machine. A header's value is read from a variable or the keychain (where the setup page stores a value typed into it), and is never written to a file, drawn or logged. A queue on disk, tried again on a network error, a 429 or a 5xx, outlives a restart and never slows a delivery. The gear's row says how many destinations are on, with its dot where one has stopped working. A trace is a view of a record, never evidence: nothing a destination answers is used.
- **Runs, one page of runs across pipelines, with filters.** The sidebar's Runs opens `/runs`, drawn as asked from the run index: filters for the pipeline, whether the records agree, the verdict against the reference, the verifier's verdict and the record's start, each a term of the search (`pipeline:`, and the new `agree:`, `word:`, `after:` and `before:`), which a filter writes into the search box. The runs list's words, newest first, 50 runs a page, with how many of the runs listed the verifier FAILs and the filter that lists them. Every run stored is still listed, sealed, at `executions-all.html`, which links the new page. A static export writes it once, every run on one page, its filters named with the line that they need a running console. Each run's row has a Steps column, one mark a step in recorded order, read from its receipts: it ran, its last attempt failed with an error, it was retried, it declined by its own rule, or it was not reached, each mark its own shape, with the steps that did not simply run named in the row's words. Each run's start has a timing bar, its length the run's duration on one scale for the page, the page's longest run, which the page states; split by step where the receipts' times read, and "no recorded times", with no bar, where they don't. A duration under a second is said in milliseconds. The marks and times are kept when a run is checked, so the list reads no receipt; a run checked before is derived again at start-up. With one pipeline chosen, a line above the table asks for a time and posts the first-run-to-leave page's own form, and each run's start links into it; with none, it says to choose a pipeline. With one pipeline chosen, the pipeline page's picker of two of its runs is drawn under the filters, posting Compare as it does there (the visitor's picker on a public console, the local picker on a local one), with the pairs already compared listed first, each opening at once. A static export draws neither.
- **Investigate: a comparison's pages, titled with the pair, as tabs.** A comparison's pages keep their addresses and are titled "Investigate · <baseline> → <candidate>", where each was "Diff". One row of tabs links them, with no script: What changed (`diff/<key>.html`), Proof, the text diff where the comparison has one shown, and Authorization (`diff/<key>-authorization.html`, new): both runs' gated steps side by side, one row a step, the first difference's step first, each run's decisions, permit and outcome as its record holds them. Where neither run gates a step or cites a decision, the tab says so, and it is never counted as a pass. It reads each record's own rows, so it is the same with the onedoor extension off. A run's Authorization page is likewise its third tab, beside its two views, at its same address. A run page's "What changed?" moves to the top, under the run's head, above the case; a held comparison opens as Investigate, with its short answer. Under its head, a comparison of two runs of one pipeline links to that pipeline's picker on the Runs page ("Compare another pair"); a static export takes it out. On the public demo, "Busy, try again" keeps its `Retry-After` and links back to the picker with both runs still chosen. On a local console, a press that waits also puts its busy words in a polite live region beside it, which a screen reader says at once. On the Runs page and on a comparison's What changed tab, the first focusable item is a skip link ("Skip to the runs", "Skip to the first difference"); at 760 px and below, a page's row of tabs stays one row, scrolling sideways in its own labelled region.
- **Re-runs and checks' runs, shown as what they are.** A run onetrace re-ran (`onetrace reproduce`, a twin, a counterfactual, or the run a check of `reproduce` produced) is labelled as onetrace-verify says it, "<kind> of <run>", with its kind's runs and step: on its row on the Runs page and on its head, each run linked where this console holds it. A check's own run (`onetrace check`) is labelled "a check's run", with its verb. Neither is offered as a reference: such a run can't be marked a benchmark, its page says why, and it is never one of a benchmark's repeats. Kept when the run is checked; a run checked before is derived again at start-up. Where onetrace-verify FAILs a run's `re-run mark`, nothing is drawn from it.
- **Each step's effect label.** Where a step's receipt records its effect (`effect_label`: read, write or unknown, and its basis: declared on the stage, a model call, an HTTP method, not classified, or put in by a check or a counterfactual), its page has an Effect section with the value and basis in the record's words, and what a label is not; the Runs page's Steps column names each value with its steps. A step with no label gets none, never "read", and a label onetrace-verify FAILs is not drawn from. A re-run stopped before a step labelled write already says so in its ending, on its head and in the Closed column.
- **What a stored check came back with.** On the head of each run a stored `onetrace check` names as its baseline or candidate, by its chain head: "confirmed by a check", "not supported by its check" or "the check did not run: <reason>", in onetrace's words, the check's own run linked, with what neither word is. On the check's own run: its verb, the runs it names (each linked where held), the step it started from, what it predicted and what came back.
- **The configuration comparison shows kept values.** Where both steps kept their configuration (`config_kept`, the file under `config/`, its bytes matching its recorded digest and onetrace-verify failing neither of its rows), a run's configuration against its pipeline's reference lists each key with both values, after the fingerprint. A key a step kept in part left out reads "not recorded", never "same". Nothing is drawn from a file that doesn't match, or where either step kept none.
- **How a model call ended, and a self-hosted call's engine.** Above a model-call record's fields on its step's page, a record in `model-call-record/1.1` says how the request ended, from its `output.finish`: its value where observed ("stop", "stop-string"), else its state and the reason it gives ("not observed: the call failed after post"). Where the record observes its engine as `vllm`, it names the engine's `model_runner`, `engine_core` and `executor`, each where recorded. A record that holds neither, or a record in 1.0, gets nothing.
- **The frame folds on a narrow screen.** Below 600 px the frame is one bar: the brand, the settings button on a local console, the demo's banner folded to its own first sentence, and a Menu button; each opens on a press, the banner whole and the links and footer under the bar, and closes on Escape or a press outside. They are the browser's own popovers, with no script, so a public console and a static export fold the same. No link or word of the frame is lost, the skip link stays first, and nothing moves on its own. At 600 px and above the frame is as it was. Below 600 px a page's title is a size smaller, and the page keeps 16 px each side. Tables stack as cards below 1024 px, where before they stacked below 761 px, so they fit beside the navigation at tablet widths. Below 600 px the Runs page's rows show each run's start, whether its records agree and its verdict; its other columns, and the timing bar, are left out at that width. On a comparison's page the short answer now ends within the first 900 px at 390 px too.
- **Each run against the first, on the Runs page.** With one pipeline chosen, the Runs page has a column "Against the first run": each run of the pipeline against the first run this console received of it, oldest first, as `onetrace drift` reports it, one mark a step drawn as the Steps column draws its marks, each its own shape, with the command's own line ("against 1: diverged, first difference b"). The first run to leave the first is marked, and a line counts how the runs listed read: diverged, identical, refused or could not check, and not compared, a refused comparison never counted as no drift. A run or a step the report does not reach reads "not compared": unknown, never as no drift. A public console draws only the reports it keeps; a local one makes a pipeline's report when it builds its run index, as its drift page does.
- **Search engines index a public console's Overview only.** Every other page a public console serves, and every page of a static export, carries `noindex`; the Overview names its canonical address where the deploy gives the console its own (`ONETRACE_CONSOLE_PUBLIC_URL`), and `/robots.txt` lets search engines crawl so they read it. The hosted demo's run pages take new addresses with each build: the old addresses already reported as not found drop out of search over time, and nothing is redirected, as those runs no longer exist. A console on this machine is unchanged.
- **Teams: every run in one team from the moment it arrives, each team's own pages, and a switcher.** With `teams` in the configuration file, each team named with how people join it (`role_claim`, an app role's value in the Entra ID token, or `scim_group`, an Entra ID group SCIM provisions), every run has exactly one team, and nothing the uploader writes chooses it. A delivered run takes the team of the ingester token that delivered it, each token bound to one team when it is made (`onetrace-console token create <principal> --team <team>`); a folder console's runs take its `folder_team`. `onetrace-console run assign --unassigned <team>` gives a team to the runs a store held before teams, and `run assign <run key> <team>` moves one run, its old address leading to the new one for those who can see it there. It does not read a team from anything in a run, and a run's key does not show its team. Teams need sign-in through Entra ID: a public console has none, and the console's own accounts cannot be in one. The pages are drawn once for each team, from that team's runs, its comparisons and what is kept about them alone, beside the all-teams set. A person reads their first team's pages at `/` and each of their teams' at `/t/<team>/`; an admin reads the all-teams set at `/`. Another team's page, run or comparison answers as one that does not exist (`404`), the same answer a key no team holds gets. The footer names the team a page is of and links to the person's other teams, an admin's ending with "All teams"; they are plain links, with no script, and list only teams the person is in. A person in no team gets one page, whatever they ask for: "You are in no team. Ask your administrator to add you." Without SCIM a person's teams are the app roles their ID token held at sign-in, so a change in Entra ID reaches them at their next sign-in; with SCIM they are read from its Groups on every request, and an app role grants no team. With sign-in off, teams scope nothing: this machine's user reads every team, and the console says so at every start.
- **SCIM provisioning from Microsoft Entra ID.** With `scim.enabled`, beside sign-in through Entra ID, the console is a SCIM 2.0 service provider at `/scim/v2`: discovery (`/ServiceProviderConfig`, `/Schemas`, `/ResourceTypes`), Users (listed with a `filter` of `eq` on `userName` or `externalId`, created, read, replaced, patched and deleted) and Groups (the same, their `filter` of `eq` on `displayName` or `externalId`). Of a User it keeps the console's id, `externalId` (the person's Entra ID object id), `userName`, `displayName`, `active` and the work e-mail; every other attribute is accepted and dropped. Entra ID calls it with a token made on the console's machine (`onetrace-console scim token create [--days <n>]`, 90 days unless `--days` says otherwise, up to `scim.token_max_days`, which is 180 by default and 365 at most; printed once and kept as its hash; at most two live; `scim token revoke <id>`), read from `Authorization: Bearer` alone; `scim.allowed_sources` limits the addresses that reach it. With `scim.required_for_sign_in`, on by default, an Entra ID sign-in is admitted only for exactly one active User with that object id in the configured tenant, checked on every request: when SCIM deactivates or deletes a person, their sessions end at their next request. On the machine, `scim user activate <externalId>` sets a User active again, and `scim enforcement off` admits sign-ins on their app roles alone, with no team from SCIM, said at every start until `scim enforcement on`. It does not write to Entra ID, and `/Me`, `/.search` and `/Bulk` answer `501`. A public console, a console in local mode, and one with sign-in off or with its own accounts refuse to start with SCIM on.
- **The audit log.** With `audit.enabled`, who did what to which run, team or person is kept in `<store_root>/audit_log/`: one line of JSON per entry, each holding the sha256 of the one before, append-only, in numbered segments. Every append also writes the newest entry's digest to `audit.head_location`, a file on another volume than the store's. Recorded: sign-ins, refused sign-ins, sign-outs and ended sessions; accounts made; tokens made and revoked; a tokenizer removed; expectations checked; SCIM's writes and tokens, and its enforcement turned off and on; runs uploaded and assigned; settings, teams and trace forwarding changed; explanations sent and completed; checkpoints and exports. `onetrace-console audit verify <folder>` checks the chain, `HEAD.json`, a checkpoint and the digests written off the volume, and prints a line per check; it is also `audit_verify.py`, one file that runs on Python 3.10 or later with nothing installed. `audit checkpoint` records the head as an entry, and `audit export <new folder>` copies the log with the verifier and a `SHA256SUMS`. When an append fails the action is refused, except one that removes access, which is applied, said, and recorded by the next append that succeeds. Reading a page is not recorded, and nothing is ever removed from the log (see Known gaps). A cut or rewritten tail shows only against the digests kept on the other volume or a checkpoint kept elsewhere.
- **Admin pages for people, teams and the audit log.** An admin's `/admin/people`, `/admin/teams` and `/admin/audit`, each drawn when it is asked for, from no run. People: SCIM's Users, each with `userName`, `displayName`, work e-mail, `externalId` and whether active, an `externalId` not shaped like an Entra ID object id flagged; the SCIM tokens and when each expires, warned from 14 days before; the requests refused from outside `scim.allowed_sources`; the values dropped beside a removal, and the writes refused that would have removed access. Teams: each team with its `scim_group` and `role_claim`, the Groups no team names, and the teams that name no provisioned Group. Audit: whether the log is on, its last entry and head, its second location, and the actions not recorded since an append last failed. Each page says at its top when SCIM's enforcement of sign-in is off and since when, and when the audit log is failing. They change nothing: people and Groups are changed in Entra ID, teams in the configuration file, and tokens and SCIM's enforcement on the console's machine. With the console's own accounts every session is a viewer, so no one reads them.
- **Teams' start-up rules.** A console that would scope or record access wrongly refuses to start, and says why and its fix. With teams: under the console's own accounts; with no live ingester token (but a folder console); with a live token bound to no team, or to a team the configuration does not hold, each named by its id; holding a run with no team, or with a team the configuration does not hold, with how many and `run assign` to fix it; and a folder console with no `folder_team`. With teams or SCIM, with `audit.enabled` false. With the audit log on, with no `audit.head_location`, its folder missing, or on the store's volume. With SCIM, on a public console, in local mode, with sign-in off, or with the console's own accounts; a public console with teams is a configuration error. Teams with sign-in off, and SCIM's enforcement off, start, with a warning at every start. The rules are checked at start only, and none of them repairs a store: each says the command or the setting that does.

### Changed

- **The run index is `onetrace-console-run-index/0.3`.** The index the runs search reads gains each step's kind and agent, and the run's agent, for the search's new `kind:` and `agent:` terms (`kind:tool-call`, `agent:triage`), each step's store writes (the store, the key's digest, the version and the digest), from which a step's page lists the other runs that wrote what it read, and each run's origin, the run its request started at, from which `origin-<run id>.html` lists every run from one request. A local console whose index is in an earlier format writes it again in the new format when it next draws its pages. A public build whose index an earlier build wrote says so on its search page and refuses the search: build it again with this version. `store_read` reads 0.3 only.
- **The hosted demo no longer records the P10 pair a second time beside the kept runs, so it shows four runs and one comparison fewer.**
- **onetrace 0.9.0 and onetrace-verify 0.9.0.** The console installs them, pinned by hash from PyPI, so `pip install onetrace onetrace-console onetrace-explain onetrace-auto` installs onetrace 0.9.0, onetrace-explain 0.3.2 and onetrace-auto 0.9.0 into one environment. onetrace-explain 0.3.1 and earlier take no onetrace 0.9, so both readmes, the Explain panel and the Set up Explain page give `pip install "onetrace-explain[keyring]>=0.3.2"`.

### Fixed

- **A request whose handling fails is answered, never dropped.** Any error the console did not catch while answering a request gets a 500: a browser asking for a page meets the console's page for it, and any other client the 500 line, each with a short reference. The full error, with the request's method and path (never its query), goes only to the console's own log under that reference: on a public console as its one JSON error line, which now carries `reference`, `method` and `path`. No traceback, file path or exception text reaches the answer. Until now a GET whose handling failed closed the connection with no answer. A failure after the answer has started is logged, and the connection closed.

- **"Sign in with Microsoft" works in Chrome, Edge and other Chromium-based browsers.** In 0.8.0 the button did nothing there. It was a form, and every response the console sends carries a Content-Security-Policy with `form-action 'self'`; a Chromium-based browser applies that to the redirect a form is answered with, here the one to Microsoft's sign-in page, so it blocked the sign-in and said so only in its developer console. The sign-in button, a refused sign-in's "Start again" and the signed-out page's "Sign out of Microsoft too" are now links drawn as buttons, and the policy is unchanged. Firefox and Safari were not tested. 0.8.0 gets no release of its own for this.

### Security

- **Forwarding reads only the variables made for it.** A destination's key comes from a variable whose name starts with `ONETRACE_FORWARD_`, or from the keychain; a destination naming any other variable is refused when it is set, and such a variable is never read to send. An admin could otherwise have sent any variable of the console's environment, the sign-in's client secret among them, to an address of their own. The setup page says so.

### Known gaps

- The audit log has no `audit prune` and no `audit.keep_days` yet: it is kept whole, every segment, until a release builds them.
- A change of `audit.head_location` is not recorded as an event of its own yet.

## [0.8.0] - 2026-11-16

- **A signed-in write from another origin is refused.** With sign-in on, a state-changing request carried by a session cookie whose `Origin` header, or else its `Referer`, names another origin than the console's own gets `403`, before its body is read. The console's own origin is `sign_in.public_url` where it is set (behind a TLS-terminating proxy, the address your browser opens), else the request's own scheme and `Host`. A request with neither header goes on to the CSRF check, as before; an ingester's bearer-token request is not checked by origin.
- **Sessions per account.** `sign_in.max_sessions_per_account` (default 3) bounds an account's live sessions: a sign-in beyond it ends that account's oldest. `onetrace-console admin sessions end <account>` ends all of an account's sessions, a running console's too. A cookie whose session is ended gets the sign-in page.
- **The sign-in limit behind a proxy.** `sign_in.trusted_proxies` (addresses and CIDR ranges, empty by default) names the proxies in front of the console. Only where a request comes from one of them, the per-client sign-in limit counts the rightmost `X-Forwarded-For` entry that is not one of them, so a client can't choose its own address by writing the header's left; otherwise it counts the connection's own address, as before. `OPERATOR_README.md` says how to set it behind the TLS-terminating proxy it documents.
- **The settings row names the model again.** Where Explain's configuration keeps its key in the keychain and a key is stored, the menu's Explain row reads "Explain: <model> (<provider>), key stored", as the row for a key in a variable names them. "Explain: no key stored" and "Explain: the keychain can't be read (<its type>)" are unchanged.
- **Explain uses only its own environment's onetrace-explain.** The console looks for `onetrace-explain` in its own Python's scripts folder and beside that Python, and no longer falls back to one found on `PATH`. Where neither place holds it, the Explain panel says so and gives the install line for this environment, the Python this console runs from quoted as this machine's shells take it.
- **A tokenizer zip with two files of one name is refused, naming both.** A zip's members are taken by their file name, a folder's name left off, as 0.7.0 says; where two members have the same file name, the refusal names both as the zip holds them: "the zip holds two files named tokenizer.json: 'a/tokenizer.json' and 'b/tokenizer.json'".
- **An unrecorded gap says what would include the run.** On the first-run-to-leave page, a gap whose records could not be checked and whose reason is not recorded reads "The reason is not recorded. It is included once a check of its records runs.", as every other gap says what would include it.
- **The skin's tokens are a module of their own.** The viewer reads the onetrace Console Skin's token block from `viewer/skin_tokens.py`, byte for byte the block it read from the vendored skin note before, and checks its sha256 as before; every page's stylesheet is unchanged. The note no longer ships in the wheel or the sdist.
- **A run's Authorization page lists its gated steps.** Where a run declares a gated step or cites a decision, its Authorization page has one row per gated step, from the record as onetrace 0.5 to 0.7 writes it: the step, its decision references, its decisions as recorded in call order, the permit if any, and the step's outcome as recorded, with onetrace-verify's own words where it read the step as acting on a decision that did not permit it; below, the verifier's `decisions:` rows. The page says it shows what the record holds, not whether a decision was right. It is a viewer page on a local and a public console, and read-only in a static export. A run with no gated step reads "No records", as before.
- **A stranger's guesses can't keep an account's owner out.** A right password sets a device cookie (`onetrace_device`, 90 days, under a key kept beside the accounts). An attempt carrying a valid one for the account it names counts only in that browser's window, 5 wrong in 900 s. Any other attempt counts in its (account, address) pair's window, 5 in 900 s, and in the account's ceiling over all addresses, 100 in 3600 s. A right password resets the pair and the browser, never the ceiling. The numbers are the new `sign_in` settings `rate_limit_max_attempts_per_device`, `rate_limit_max_attempts_per_pair`, `rate_limit_pair_window_seconds` and `rate_limit_account_window_seconds`, and `rate_limit_max_attempts_per_account`, whose default is now 100. While an account is at its ceiling, a new browser reads "too many sign-in attempts for this account from new browsers; sign in from a browser you have used before, or ask an admin", in the same words and status for a name with no account. `onetrace-console admin unlock <account>` clears the ceiling, and `onetrace-console admin device-key rotate` ends every device cookie.
- **A run folder's `.lock` is read for what it names.** A `.lock` naming a process on this host that is gone is the recorder's, left by a run stopped without closing: the folder is loaded without it, and the run reads "not closed". One naming a live process on this host is skipped, as before. An empty `.lock`, as every onetrace before 0.9 writes it, or one naming another host, lists the folder on the Runs page under "Locked run folders": "locked: still recording, or stopped without closing", or "locked: recording on another host, or stopped there without closing". Where a folder is watched, a local console offers "Load as not closed" beside an empty one; a public console only lists it.
- **OPERATOR_README's configuration example holds every key.** The example shows every key the console reads, each at its default but the container's store root, and the table beside it says what each one means, `extensions`, the decision-export limits, `tsa_cert` and `tsa_roots`, Compare's seven keys and `tracing` among them.
- **L3 at the first difference, and model-call records in 1.1.** A step's model-call records in `model-call-record/1.1`, which onetrace 0.7 writes for a call captured at L1, L2 or L3, are read as 1.0's are, held to the installed onetrace's own rules; a hosted capture's steps file, which holds text, draws no timeline of ids. Where both runs' model calls at a comparison's first differing step kept an L3 capture, the page gives the first token whose logits-row digest differs, the first whose chosen token differs, and how many positions before it had a changed row and the same token, with the capture as recorded: level, digest method, model runner, batch-invariant mode. Only delivered tokens are compared; the surplus is shown, never compared. One run at L3 and the other not, or two digest methods: "not comparable", and why. Unless both runs' records verify: "couldn't check". With batch-invariant mode off, the page says a changed digest can come from how requests were batched, not from the model. A digest difference is not a verdict and changes none.
- **L2 at the first difference.** Where both runs' model calls kept an L2 capture (self-hosted ids, L3 with them, or the hosted form), at the first token whose choice differs the comparison's page says whether each run's token is among the other's top-k there and its rank, or that it is not, with k as recorded, beside the L3 reading where there is one. A self-hosted call shows ids and ranks: the console loads no vocabulary. A hosted call, on a local console, shows the candidates' text, labelled "model-generated, as the provider returned it". A public console shows ranks only, and text or ids only for the demo's own example data, labelled so. The capture as recorded sits beside it: level, k, log-probabilities and the sampling parameters; where sampling was not greedy, a token outside the other run's top-k can come from sampling alone. Mixed levels or a differing k: not comparable. Where a run kept no steps file, the section says so and shows no candidate or rank. A rank shows how the candidates were ordered, not why one was chosen, and changes no verdict.
- **Close calls on a model step.** On a model step whose record carries L2 with log-probabilities (the hosted form), the step's page flags the positions where the chosen token's lead over the runner-up is at most `close_call_margin`, a new setting in nats (default 1.0, above zero), and shows the first such position and a count. Without log-probabilities, as a self-hosted capture holds ids only: "no log-probabilities recorded"; without L2, nothing. The words are a fact of the capture, labelled model-generated, under the same text rules as L2's: no real run's text on a public console. A close call is not an error, and a wide margin is not correctness.
- **The capture store.** `onetrace-console demo --public --captures` builds and serves a small store of its own, beside the demo: three runs of the demo's agent whose self-hosted model call is captured at L3 (a logits-row digest per token, with the top-k), example data constructed through onetrace's own writer, no model called. A baseline; a run whose logits row changes before its chosen token; one with batch-invariant mode off; the baseline compared with each. Its comparison pages show the model's rows and choices at the first difference, and its runs' ids show as the builder's own example data, labelled so. With `--build <folder>` it builds into a folder and exits, as the public demo does. The demo's own runs, counts and comparisons are unchanged.
- **Upgrading no longer shows the previous release's demo:** each version builds its own demo folder, and an older one is named at start-up, never used.
- **One button style.** Every button the console draws is one of three styles, from the theme's tokens in both themes: primary for a form's main action (Sign in, Save, Search, Compare, Find the first run to leave, Check, Use this tokenizer, Confirm and turn on, Explain, Send), secondary for every other press, and destructive for a removal (the stored key's Remove, a tokenizer's Remove). Each has a hover state, a visible focus outline and a disabled state, and its text reads at 4.5:1 or more on its own background in both themes, disabled too. Before, most were the browser's own grey buttons, grey on grey in the dark theme.
- **One key field on Set up Explain.** With a key stored, the model form shows no key field and its Save keeps the stored key, saying so beside the button; the key section below has New key and Replace in one row, and Remove on its own row under "Remove the stored key". With no key stored, the model form keeps its key field, and a locked keychain or none reads as before: the page has one key field, or none.
